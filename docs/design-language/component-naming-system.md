# Component Naming System

## Summary

The naming framework translates the product narrative into interface terminology. Components are named to reinforce the navigation and strategic charting metaphor rather than generic business app categories.

## Key Rules

- Use strategic navigation terminology for high-level patterns.
- Keep names aligned to the product’s operating metaphor.
- Prefer domain meaning over generic UI labels.

## Allowed Patterns

- Bridge = executive navigation center.
- Chart = dashboard view.
- Star = objective.
- Course = initiative or execution path.
- Bearing = recommendation or directional suggestion.
- Fleet = portfolio or business-unit grouping.
- Position Fix = strategic assessment.
- Weather = risk or disruption context.

## Reusable Hierarchy Controls

- Tree components should be named as navigation instruments, not generic file explorers.
- Preferred naming: Polaris Tree View or Polaris Disclosure Tree.
- Use disclosure language (expand/collapse) only for control semantics, not as primary component identity.
- Node labels should emphasize strategic identity (organization, role, status) over technical IDs.

## Forbidden Patterns

- Generic dashboard, widget, or project labels that flatten the product metaphor.
- Names that are not meaningful to executive strategy users.
- Inconsistent usage of navigation terminology across the interface.
